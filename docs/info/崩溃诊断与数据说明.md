# 崩溃诊断与数据说明

2.52 在地图随附的 X_JAPI 加载链中加入了客户端崩溃现场记录与下次启动补报。它用于区分地图脚本、游戏本体与第三方模块附近的异常，帮助定位长时间游玩或副本战中的闪退；记录失败、网络不可用或组件未加载都不会阻止地图继续启动。

!!! info "能力边界"
    这套机制只能记录**当前客户端进程**可取得的有限现场，不保证每次闪退都有完整 JASS 调用链，也不会代替 Warcraft 自带的错误报告。JassDebug 等第三方工具生成的本地诊断文件，也不等同于已经自动上传。

## 崩溃与补报流程

1. 地图启动时在 Warcraft 根目录的 `Logs/DaoCrash` 建立本局会话标记，并记录地图构建、游戏模块校验结果和有限的模块摘要。
2. 正常游玩期间只在会话、Boss、主线、存档和读档等低频节点更新少量“面包屑”，不进入伤害或计时器的高频路径。
3. 发生未处理异常时，捕获器先把原生异常上下文写入本地 `pending_*.bin`；游戏版本与 JASS 虚拟机结构兼容时，再尝试附加当前函数、最多 8 层调用现场和指令位置。
4. 崩溃处理阶段**不会发起网络请求**。下次启动地图时，才会结合 pending、会话标记与 Warcraft `Crash.txt` 的时间关系生成 `client_crash_report`。
5. 只有服务器返回成功响应后才删除 pending；断网或超时会保留到以后重试。

证据会按可靠程度分级：

| 等级 | 含义 |
|---|---|
| Q2 | 捕获器已经写下原生异常上下文 |
| Q1 | 没有原生 pending，但在会话时间窗口内匹配到 Warcraft `Crash.txt` |
| Q0 | 只能确认上次会话没有正常收尾，不能据此断言一定发生了崩溃 |

## 本地文件

| 位置 | 用途 |
|---|---|
| `Logs/DaoXBootstrap.txt` | 组件版本、加载结果、本地文件开关与失败原因 |
| `Logs/DaoCrash/` | 会话标记、心跳和待补报的崩溃现场 |
| `Errors/* Crash.txt` | Warcraft 自身生成的错误报告；诊断组件只做时间关联与摘要 |

正常退出或会话正常结束时，会话标记会被清理。若发生闪退，建议先重新启动一次 Warcraft 并进入 2.52 地图，让待补报现场获得一次发送机会；在此之前不要手动删除 `Logs/DaoCrash`。

## 上传内容与隐私边界

崩溃报告不会上传 `Crash.txt` 全文、内存转储、用户名或绝对文件路径。当前报告只包含定位问题所需的有限元数据，例如：

- 地图版本、构建标识、证据等级与事件编号；
- 异常代码、模块名与模块内相对位置；
- 相关文件的名称、大小和 SHA-256 摘要；
- 有固定数量上限的模块摘要、地图面包屑；
- 环境兼容时取得的有限 JASS 函数与调用现场。

网络链路不可用时只会关闭或延后诊断上报，不影响原有 X_JAPI 功能和正常玩法。

## 与存档诊断的区别

`-savediag` 专门检查本地存档读写、注册表和文件落点，详见[存档与读档](存档与读档.md)。它不会主动制造崩溃，也不是查看崩溃报告的命令。
